# Runtime API политик подписок

API version 1: `xray.app.policy.command.SubscriptionService`, схема в `app/policy/command/command.proto`. Это расширение ElXray.

## Включение

Добавьте `SubscriptionService` в `api.services`, задайте `api.listen` явным loopback-адресом (`127.0.0.1:10085`, `[::1]:10085`) либо защищённым Unix socket. Routed API без явного listen, `0.0.0.0`, LAN-IP и hostname вместо literal loopback отклоняются при сборке JSON. На уровне RPC также проверяется локальный TCP/Unix peer.

Штатный Commander не аутентифицирует локальные процессы. API предназначен для доверенного локального агента/панели; права Unix socket задаёт оператор. Внешний backend обращается через аутентифицированного агента, не публикует gRPC-порт в Интернет или LAN. Сам WireGuard-адрес не является учётной записью API.

```json
"api": {"tag":"api", "listen":"127.0.0.1:10085", "services":["StatsService","SubscriptionService"]}
```

## Контракт

`GetSubscription(id)` возвращает ID, серверные emails, обе скорости в **байтах/с**, revision и disabled. Новая стартовая политика без указанной revision получает 1.

`SetSubscription` требует существующий ID, expected_revision, revision = expected_revision + 1, явно присутствующие uplink_bps, downlink_bps и disabled. Пропущенное направление не превращается молча в unlimited: protobuf использует optional presence. Оба направления меняются атомарно.

- 0 байт/с в стартовой конфигурации означает unlimited. Runtime RPC отклоняет ноль в любом направлении. Безлимит задаётся через конфигурацию, доступную администратору.
- disabled=true — запрет передачи полезных данных в обоих направлениях. Ожидающие бюджет операции просыпаются с ошибкой. Это не механизм отзыва ключа или принудительного закрытия каждого idle socket; уже переданные downstream/kernel байты отозвать невозможно.
- Изменение действует на существующие обёрнутые соединения; unlimited → limited также работает. Меняется скорость, а не объект бюджета. Накопленный burst не сбрасывается при обновлениях.
- Точный повтор уже принятой операции возвращает текущее состояние без нового burst. Другая политика с устаревшей expected_revision возвращает Aborted.
- Неверные поля/скорости — InvalidArgument; неизвестный ID — NotFound; удалённый peer — PermissionDenied. Ошибка сохраняет last-known-good состояние.
- Создание, удаление и изменение email-привязок через этот API не поддерживаются. Их обновляет стартовый конфиг с перезапуском. Удаление политики не используется как снятие ограничения.

```powershell
.\xray-lab.exe api subscription-get --server=127.0.0.1:10085 --id=lab-account
.\xray-lab.exe api subscription-set --server=127.0.0.1:10085 --id=lab-account --expected-revision=1 --revision=2 --uplink-bps=312500 --downlink-bps=625000 --disabled=false
```

Получится upload 2,5 Мбит/с и download 5 Мбит/с. Для следующего изменения сначала прочитайте revision. Повтор команды выше безопасен; при конфликте перечитайте состояние и решение оператора, не увеличивайте ревизию вслепую.

## Восстановление

Ядро держит runtime-изменения в памяти, не переписывает JSON панели и не является хранилищем тарифов. `revision` и `disabled` поддерживаются в стартовом `policy.subscriptions`.

Управляющий процесс должны сохранять желаемое состояние в своей БД до отправки, фиксировать подтверждённую ревизию, повторять потерянные доставки и перед запуском ядра формировать конфиг из сохранённого состояния. При конфликте desired/applied показывать оператору реальный статус. Откат — новое обновление с новой ревизией. Без такого supervisor перезапуск вернёт параметры из исходного JSON.

Для исключения unlimited при пропущенной привязке включайте `policy.requireSubscription: true`: аутентифицированный пользователь без политики, включая пустой email, не передаёт данные. Это не заменяет согласованную запись новой подписки/пользователя в панель. Неаутентифицированные служебные потоки этим флагом не превращаются в VPN-подписку.

## Ограничения

Бюджет независим для каждой ноды. Равные доли между потоками/устройствами не гарантируются. Ожидания без резервирования будущих токенов могут давать дополнительную конкуренцию таймеров при большом числе потоков; длительные CPU/RSS/jitter тесты обязательны. Управляемые безлимитные пользователи тоже проходят буферную обёртку и не используют raw splice: это цена последующего управления действующим соединением.

## Отключение подписки VLESS

При применении `disabled=true` ядро запрещает новые прямые VLESS-запросы подписки и закрывает зарегистрированные входящие соединения этой подписки. Закрытие затрагивает и простаивающие соединения. Смена скоростей при `disabled=false` сохраняет соединения. VLESS Reverse имеет отдельный жизненный цикл.

Это действие относится ко всей локальной подписке. Подтверждение политики по-прежнему удостоверяет её сохранение и применение. Оно не подтверждает остановку поколения конкретной сессии или отсутствие уже переданных в транспорт байтов.

## Подтверждение уменьшения скорости без отключения VPN

При `SetSubscription` обе скорости меняются атомарно в существующих token buckets. Это не требует нового VPN-handshake. Чтобы Control безопасно освободил часть глобального бюджета для другой ноды, одного подтверждения применения политики недостаточно: требуется подписанный `RateBarrier.Prove`.

Для положительного ограничения (`up > 0`, `down > 0`) ElXray выполняет **quiet barrier**:

1. Проверяет, что exact revision и скорости действительно записаны в durable policy store и применены в локальном ядре.
2. На короткое время приостанавливает вход новых **порций полезных данных** в rate-guarded путь диспетчера. Существующие TCP/UDP/Mux/VLESS соединения не закрываются.
3. Дожидается завершения всех порций данных, допущенных до barrier. Каждая передача защищена с момента резервирования токенов до передачи буфера следующему компоненту диспетчера.
4. Ещё раз сверяет неизменность durable revision, затем подписывает привязанный к entitlement/node/resource/operation/epoch/revision и обоим скоростям transcript. После завершения proof снимает паузу.

При таймауте или смене политики доказательство **не выдаётся**. Control сохраняет старое обязательство по скорости до успешного signed readback и `FinalizeRateMove`; ошибку нельзя интерпретировать как освобождённый бюджет. Для полного отключения (`disabled=true`, целевые `up=down=0`) остаётся **строгий drain всех активных потоков**, а не quiet barrier.

Это синхронизация на границе полезных данных диспетчера, а не подтверждение фактического опустошения сетевой очереди ядра ОС, физического wire-rate или TCP-буферов клиента. Эффективная скорость сохраняет конечный token-bucket burst и задержки транспорта. Для бизнес-приёмки обязательны отдельные непрерывные сетевые тесты, проверка envelope и отсутствие незарегистрированных путей обхода rate-обёртки.
